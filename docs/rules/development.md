# Процесс разработки HyperIDE

**Статус: обязателен к исполнению.** Этот регламент описывает полный цикл работы над
изменением — от тикета до релиза. Нарушение этапов недопустимо (типичные нарушения
перечислены в конце). Применяется ко всем агентам (основной Claude, субагенты, Codex).

Связанные регламенты:

- [Запрос решения CTO](./cto-decision-requests.md) — когда и как эскалировать решение.

## Этап 0. Создание Linear-тикета

- Каждый баг / задача → отдельный тикет `HYP-XXX`.
- Ветки называются строго: `HYP-XXX-short-description`.
- **Без тикета — нет ветки, нет коммита.**

CLI: `linear issue create --team HYP --title "..." --description "..." --no-interactive`.

## Этап 1. Диагностика (root cause first)

По навыку `/systematic-debugging`:

- Читаем стектрейс / воспроизводим баг.
- Проверяем recent changes (`git log`, `git blame`).
- Собираем evidence послойно.
- **Не предлагаем фиксы, пока не найден root cause.**

## Этап 2. Реализация в worktree

- Worktree создаётся **только** в `/Users/ultra/work/hyper-canvas-draft-worktrees/`.
  НЕ в `.claude/worktrees/` и НЕ внутри основного репозитория — это нарушение.
- **TDD обязателен:**
  1. Пишем failing-тест (красный).
  2. Запускаем — убеждаемся, что падает по нужной причине.
  3. Пишем минимальный код, чтобы тест прошёл.
  4. Тест зелёный — рефакторим при необходимости.

  Никогда: сначала код, потом тест.

- Тесты: `bun run test` (не `bun test` — тот цепляет `templates/`).
- Scope тестов: `client lib server shared vscode-extension`.
- Правки только через Edit/Write; **никаких `sed`/`perl`/`awk`** для редактирования файлов.
- **E2E живёт в ОТДЕЛЬНОМ репо `ext-test-projects/`** — клонируется **рядом** с этим
  репо (по умолчанию `/Users/ultra/work/ext-test-projects/`, sibling-чекаут, НЕ внутри
  hyper-canvas-draft и не сабмодуль). Это неотъемлемая часть процесса, не внешний
  прожект. Поэтому `ext-test-projects/` и `bun run test:docker` НЕ найдутся из чистого
  клона одного hyper-canvas-draft — сначала склонируй ext-test-projects рядом. Прогон
  оттуда: `HYPER_E2E_SHARDS=1 bun run test:docker`.
- **Таймауты — зло.** Раздутые `timeout` / `poll interval` в e2e маскируют настоящий
  баг (флак, гонку, медленный старт). Запрещено «лечить» падение увеличением таймаута.
  Найти и починить root cause. Если таймаут поднят временно, чтобы разблокироваться —
  немедленно завести тикет на возврат и вернуть тесную границу, как только корень
  закрыт. Тайтовые границы держим осознанно.

## Этап 3. Перед коммитом

1. `bun run knip` — настроенный чек (не `bunx knip` — тот качает несконфигуренный
   и сыпет шум); убрать неиспользуемые экспорты / зависимости / файлы.
2. Self-review — TODO/FIXME, dead code, дубли, конвенции, comment hygiene
   (не осталось ли висящих JSDoc от удалённого кода).
3. Ревью — обязательный тандем, оба перед коммитом:
   - `advisor()` — сильный ревьюер (только главный агент, не сабагенты).
   - `codex exec review --uncommitted` — дождаться до конца, прочитать findings.
4. Убедиться, что для новой логики есть тесты.
5. `/commit` — полный чеклист (Linear lookup → commit → пост-коммит).
   **Коммитим через `/commit`, не напрямую `git commit`.**

**Коммиты всегда проходят pre-commit хуки — `git commit --no-verify` / `-n` запрещён**
(см. [development → запрет --no-verify в AGENTS.md]). Если хук чёрнит кавычки — чинить
корень (`.oxfmtrc.jsonc` `singleQuote: true`), а не обходить хук.

**Адверсариальная проверка (доказательство от обратного).** Проверяя фикс или находку,
не подтверждай «работает» — попытайся СЛОМАТЬ. Построй случай, где оно ДОЛЖНО упасть;
ищи контрпример и реальные границы. Для утверждений «больше не происходит» / «всегда
работает» обязательна попытка опровержения: если контрпример нашёлся — реши, это
намеренная граница или баг; если не нашёлся — задокументируй, какие случаи проверены.

- **Конкретные пруфы, а не пересказ.** Пруф = артефакт (отрендеренный DOM,
  сгенерированный вывод, прогон теста, скриншот), а не «хелпер возвращает пусто» /
  «по построению верно». Проходи реальный путь (рендер / генерация), не только юнит-уровень.
- **Честные границы.** Явно назови, где фикс НЕ работает (floor / edge-кейсы) —
  задокументированная граница лучше ложного «универсально».

```text
// Утверждение: "после фикса <Badge/> рендерит children всегда"
// (1) Позитив — пруф через отрендеренный вывод, не через юнит:
render(<Badge>hi</Badge>)
assert dom.text == "hi"        // пруф = реальный DOM, не "хелпер вернул 'hi'"

// (2) От обратного — найти случай, где оно ОБЯЗАНО упасть:
render(<Badge>{null}</Badge>)
assert dom.text == ""          // контрпример: "всегда" опровергнут
                               // → решить: намеренная граница (floor) или баг
```

## Этап 4. Визуальная проверка (обязательно для UI)

- Скриншоты ДО и ПОСЛЕ через Playwright / `launchVSCode` (не `screencapture`).
- Проверяем: пустые панели, обрезанный контент, неправильные ширины / наложения,
  стейл-диалоги, неактивные табы.
- **Определение «готово»: баг НЕ считается готовым, пока серия скриншотов-пруфов
  не отправлена CTO в Telegram И CTO её не принял.** Зелёный e2e, мёрдж в main,
  «всё работает» — это НЕ «готово» без принятых CTO скриншотов. Никаких ✅ / «done»
  / «исправлено» до явного апрува скринов в TG. Правило действует на ВСЕ баги, в т. ч.
  уже влитые: если пруфов в TG не было — задача открыта, пока CTO не принял скрины.

## Этап 5. После коммита

- Комментарий в Linear с хешем коммита.
- Проверка stale docs (`AGENTS.md`, `.serena/memories/`).
- Deferred findings → Linear-тикеты немедленно.
- Security / API changes → `/security-review`.
- UI changes → `/frontend-design`.

## Этап 6. Мёрдж и релиз

- Cherry-pick или PR → `main`.
- `CHANGELOG` → bump version → tag.
- `bun run package` → `publish.sh`.
- TG с release notes.
