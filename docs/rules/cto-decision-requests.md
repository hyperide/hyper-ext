# Запрос решения CTO

**Статус: обязателен к исполнению.** Регламент описывает, когда и как эскалировать
решение пользователю (CTO, Alex). Применяется ко всем агентам.

Связанный регламент: [Процесс разработки](./development.md).

---

## Когда эскалировать

Эскалировать **только** продуктовые / архитектурные решения, которые не выводимы из кода.

**Не рекомендуй — делай.** Если ты уже знаешь правильный вариант или можешь его выяснить —
не перекладывай выбор на CTO. Сначала **брейншторм** (`review brainstorm` / debate-swarm
через разные модели). **Если кворум моделей сошёлся с уверенностью — это и есть решение:
реализуй его автономно и отчитайся готовым кодом + обоснованием (со ссылкой на кворум), а не
вопросом.** Эскалируй ТОЛЬКО при реальном расхождении моделей или необратимом решении с
большим радиусом поражения без явного победителя. Пересылать CTO уже решённый кворумом
вопрос как «выбери A или B» — нарушение.

**Не вешай ярлык «риск/уязвимость/hazard» на суть продукта.** Запись, которую делает сам
инструмент (например ретаргет i18n-ключа), — это фича, а не опасность; пользователь/команда,
видящие СВОИ же данные своего проекта (ключи, тексты, исходники), — это не «утечка». Прежде
чем называть что-то риском, спроси: кому именно и чем это вредит? Если ответа нет — это не риск.

**Триггер:** любое упоминание открытого PR в TG/чате (даже «ждёт ревью» в статус-отчёте)
считается decision request и запускает этот протокол.

## Самопроверка — обязательна перед любым вопросом

Всё, что поддаётся проверке, — проверяй сам. Если ответ получается одной shell-командой —
**не спрашивай CTO**.

- `git log`, `git diff --stat`, `grep`, `curl`, `cat`, `git merge-tree` — делать самому.
- Примеры: деплоится ли лендинг из main → `grep workflows`; есть ли функция в main →
  `grep`; конфликты → `git merge-tree`; транзитивная ли зависимость → `grep package.json`.

## Консультации перед вопросом

| Кто задаёт вопрос         | advisor()               | codex exec         | claude CLI  |
| ------------------------- | ----------------------- | ------------------ | ----------- |
| Основной Claude-агент     | ✅ вызвать напрямую     | ✅ через субагент  | —           |
| Субагент Claude (фоновый) | ❌ нет доступа к сессии | ✅ напрямую        | —           |
| Codex-агент               | ❌ нет инструмента      | ❌ nested запрещён | ✅ напрямую |

1. Посоветоваться с `advisor()` (только основной агент).
2. Запустить codex review (основной → через субагент; субагент → напрямую; Codex → `claude` CLI),
   результат сохранить в `docs/reviews/`, закоммитить.
3. Формулировку review/decision request делает **субагент**, не основной агент.
   Это жёсткое правило, а не предпочтение: основной агент в многозадачности срезает
   углы — выдаёт «голую» сводку (варианты без реальных pros/cons, без ссылки на спеку,
   без «где смотреть»). Поэтому **основной агент НЕ постит запрос решения, который
   сформулировал сам по ходу дела.** Он диспетчит субагента, чья единственная задача —
   прочитать спеку/код и собрать запрос строго по «Формату вопроса» ниже.
   **Self-check перед отправкой в Telegram** (любым агентом): в сообщении есть Контекст +
   расшифровка терминов + Варианты с РЕАЛЬНЫМИ pros/cons + Рекомендация + «где смотреть»?
   Если хоть один пункт отсутствует — это нарушение, не отправлять, переформулировать.
4. Только если вопрос остался открытым — эскалировать.

## Канал: Telegram (обязательно)

Каждый decision request **должен** уйти в Telegram (через `tg` CLI) — параллельно с
публикацией в чате, немедленно при формулировке. CTO не всегда смотрит чат Claude Code.
Не «напомню потом».

**Сводный список по запросу.** Когда CTO просит «все решения» / «что ждёшь от меня» — дай
ОДНИМ сообщением в TG **единый список ВСЕХ открытых на данный момент решений**, каждое по
«Формату вопроса» ниже (конкретный вопрос + варианты с реальными pros/cons + рекомендация),
а не расплывчатой категорией («нужно решить D1/D4/D5») и не разрозненными обрывками. Веди
его актуальным: уже снятые/решённые помечай как закрытые и не повторяй их как открытые.

## Формат вопроса

Цель: **CTO принимает решение за 30 секунд, не читая код.** Поэтому:

1. **Контекст** — где находится код, `файл:строка`, что делает функция.
2. **Расшифровка терминов и названий** — любое внутреннее имя (тикет, модуль, функция,
   аббревиатура, флаг) поясняется одной фразой. CTO не обязан помнить внутренний жаргон.
   **Не выдумывай транслитерированные англицизмы** (кальки английских слов кириллицей):
   используй принятый русский термин, либо английское слово латиницей + пояснение в одну
   фразу при первом употреблении («fallback-пропы — props по умолчанию, подставляются,
   если компонент не получил настоящих»).
3. **Проблема** — что именно требует решения, конкретно (не абстрактно).
4. **Варианты** — только те, у каждого из которых есть реальные преимущества. Каждый
   вариант — **значимые и разумные pros / cons** (не формальные, а влияющие на выбор).
5. **Рекомендация** — какой вариант агент считает правильным и почему.
6. **Где смотреть код** — конкретные файлы и строки для быстрого review.
7. **Скриншоты** — если проблема визуальная: ДО (проблема) + описание как должно быть ПОСЛЕ.
8. **Псевдокод для нетривиального механизма** — 3–7 строк «до/после» вместо абзаца прозы;
   короткий сниппет понятнее параграфа. Пример:

   ```jsx
   // БЫЛО: объект-заглушка летит на любой компонент
   <Component {...previewFallbackProps} />;
   // СТАЛО: передаём только пока не пришли точные значения (gate по флагу готовности)
   <Component {...(ready ? {} : previewFallbackProps)} {...realProps} />;
   ```

9. **Дифф изменений в дочернем / смежном репозитории — обязательно, текстом в Telegram.**
   Главный случай: изменения **не в основном репо** (которое CTO видит в своём локальном
   checkout), а в **дочернем / смежном проекте** — другой репозиторий, worktree, расширение,
   CLI-утилита (например `conloca`, `tg-cli`, `ext-test-projects`, `draw-cli`). Такой код
   CTO локально НЕ видит и не будет искать сам, тем более с телефона. Поэтому:
   - Сгенерируй авторитетный дифф **из самого worktree ветки дочернего репо**:
     `BASE=$(gh pr view --json baseRefName -q .baseRefName); git diff "origin/$BASE...HEAD"`
     (три точки). Base берём из самого PR, потому что захардкоженный `origin/main` даёт
     неверный дифф для PR с другой базой (например `develop`). Он надёжнее
     `gh pr diff <N>`, который считает против сдвинувшегося base и может выдать
     неполный/искажённый патч.
   - **Приведи дифф ТЕКСТОМ В Telegram, красиво отформатированным** — НИКОГДА сырым файлом
     `tg --file <patch>`: `.patch` на телефоне не форматируется и нечитаем. Формат:
     `tg --format html`, каждый кусок диффа в код-блоке `<pre><code class="language-diff">…
</code></pre>`; длинные/второстепенные куски — в `<blockquote expandable>`
     (сворачиваемый блок). Сырые `<`, `>`, `&` внутри диффа экранируй (`&lt;`, `&gt;`,
     `&amp;`).
   - Telegram лимит ~4096 символов на сообщение — **разбивай по файлам/ханкам** на
     несколько сообщений. Сначала **ядро механизма** (production-код), потом остальное;
     крупные тестовые диффы можно резюмировать строкой, а не лить целиком.
   - Перед каждым блоком — строка «где смотреть»: `файл — назначение изменения`.
   - **Инструмент, который РЕДАКТИРУЕТ чужой код (а не меняет свой репо) — показывай дифф
     РЕЗУЛЬТАТА в правимом проекте.** Если фича = экстеншен/CLI правит файлы целевого
     (пользовательского / fixture / дочернего) проекта — например HYP-544 переписывает
     `className` в коде проекта — CTO проверяет НЕ дифф самого экстеншена, а **что именно
     записано в целевой файл**: правильно ли применён стиль И не задеты ли места, которые
     трогать нельзя. Сними дифф `до → после` именно этого целевого файла (захвати его из
     e2e до того, как тест восстановит фикстуру), плюс подтверди, что **другие файлы не
     изменились** (`git status` в целевом проекте). Дифф собственного кода инструмента тут
     второстепенен.
   - **Обязательные обходы багов `tg` (иначе отправка диффа падает или приходит мусор):**
     - Запускай `tg` из **нейтрального cwd** (`cwd: '/tmp'`). `tg` авто-детектит в тексте
       пути к существующим файлам и пытается слать их как media-group (caption-лимит 1024)
       → дифф (где путей полно) упадёт с `400`. Из `/tmp` относительные repo-пути не
       резолвятся → уходит чистым текстом.
     - Ставь `TG_AI_MODEL=claude` в env вызова — иначе авто-ярлык отправителя выдаёт мусор
       (видели `✳️ [danny's bug]`).
     - Чанк держи **≤ ~3000 символов сырого тела** (HTML-экранирование `<`/`>`/`&` раздувает
       длину; запас до 4096). Отправляй последовательно с пометкой `(i/N)`.
   - Для основного репо (которое CTO ревьюит локально) достаточно ссылки на PR +
     постатейной сводки; но если он просит показать код — присылай так же, отформатированным
     текстом, а не файлом.

**Максимально полный контекст.** Лучше избыток контекста, чем вопрос, на который нельзя
ответить не открывая репозиторий.

## Решения «PR или drop» / «открыть PR или закрыть»

Обязательно указать:

- Что конкретно реализовано (функциональность, не список файлов).
- Связанный Linear-тикет и его приоритет.
- Актуально ли по текущему роадмапу (насколько видно из кода и истории).
- Что теряется при drop (объём работы, уникальность подхода).
- Риски при merge (конфликты, регрессии, тест-покрытие).

Нельзя писать просто «нужно: открыть PR или drop» — это перекладывание решения без контекста.
