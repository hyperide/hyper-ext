Concept explainers

The ideas the spec and the landscape lean on, each with what it is, why it matters for the toolkit, and a picture. First batch — every explainer here started as a question Mextner asked. Illustrations follow one visual language and will go through the comprehension-testing protocol (R34).

Push-pull reactivity (the "converged algorithm")

push-pull с тремя состояниями — алгоритм, на котором сошлись все

When a signal is written, dependents are not recomputed — they are only marked (the cheap push phase): direct dependents become dirty, everything further becomes check ("maybe dirty"). Actual recomputation happens lazily on read (the pull phase): a node asks its sources "did you really change?", and if an intermediate computed recomputes to the same value, everything below it stays clean and untouched.

This one design gives glitch-freedom (the diamond problem is gone — you can never observe half-updated state), no redundant recomputation, and cheap dynamic dependencies. Reactively invented the three-state form; alien-signals, Preact Signals, Svelte 5, Solid 2, Vue 3.6 and the TC39 proposal are the same algorithm with different constants (linked lists vs arrays, flags vs version counters).

Why it matters for us: this is §4.1 of the spec — vendored (alien-signals form) behind a 5-function interface. R41 adds: publish it as an isolated, seriously-tested standalone package, benchmark the internal variants (lists vs arrays, flags vs counters) against each other, and make the variant switchable behind the same interface.

Two-phase batch

почему 100 записей подряд — это один пересчёт, и ни одного глитча

Phase one: every write in a batch only marks the graph (see above) — nothing computes, no effect runs. Phase two: when the batch ends, one lazy pull recomputes what is actually needed and each effect runs at most once, never on intermediate state. Svelte 5 and Solid 2 end the batch on a microtask (so even synchronous reads see the old value until flush()); Preact/Vue flush synchronously at batch end.

We take two-phase, but with a synchronous second phase at the end of the outermost transaction (§4.1): controlled React inputs need the write visible within the same event (caret position, IME composition), and useSyncExternalStore demands a consistent snapshot. Same guarantees, without the "why is my value stale until flush()" surprise.

Why it matters for us: §4.1's single pipeline — mark → sync effects → sync notify → bus listeners in a microtask — is exactly this, tuned for React's input semantics.

Copy-on-write (COW) & structural sharing

COW = копируем только то, что трогаем; всё остальное — общее между версиями

COW: to "modify" an immutable tree you copy only the containers you touch plus the path up to the root; every untouched subtree is shared by reference between the old and new version — that sharing is structural sharing. A change to one field of one item costs a handful of small object copies, old snapshots stay valid, and "did this subtree change?" is a reference equality check. Immer, Mutative, our transaction engine (§4.4), and — at page granularity — LMDB and CouchDB all work this way.

Why it matters for us: R2 + R9 by construction: mutable-looking writes in a transaction produce a structurally shared snapshot plus RFC 6902 patches. Cost model: O(size of each touched container) — which is why big hot arrays are normalised into keyed collections (ids + byId), making the touched container a single item.

HAMT — and why databases use B-trees anyway

HAMT = hash array mapped trie; и это не противник structural sharing, а его другой носитель

A HAMT (hash array mapped trie) is the persistent hash map behind Immutable.js, Clojure and the C++ immer library: the key's hash is consumed 5 bits at a time, each level is a node of up to 32 slots (compressed via a bitmap), so any update copies ~log₃₂ n small nodes and shares the rest — structural sharing with O(log₃₂ n) updates independent of container size, versus COW's "copy the whole touched container".

Databases still choose B-trees because their unit of cost is the 4–16 KB disk page, not the pointer hop: a B-tree with fanout in the hundreds reaches billions of keys in 3–4 page reads, keeps keys ordered (range scans), and maximises useful bytes per page. HAMT's many small scattered nodes are cache- and disk-hostile. The twist: LMDB and CouchDB are copy-on-write B+trees — databases already do structural sharing, at page granularity. In memory, in JS, the "page" is a plain object, so COW-of-plain-objects wins for typical UI containers; HAMT only pays off for very large, hot, unordered maps.

Why it matters for us: the core stays COW-of-plain-objects (§4.4). Per R52, Immutable.js is not discarded: it is faster than Immer while you stay inside its structures and never call toJS() — the conversion tax at every React/JSON boundary is what killed it in practice. A HAMT-backed collection storage variant behind the same interface is a legitimate experiment for 100k+-entry maps; the compiler could even pick storage per collection from observed sizes — measured, not assumed.

Hydration vs resumability (Qwik)

гидрация выполняет всё приложение заново; resumability продолжает с места, где сервер остановился

Hydration (React, Vue, Svelte, Solid SSR): the server renders HTML, then the client downloads the components and re-executes them all to rebuild state, closures and event handlers, then attaches listeners. You pay for the app twice.

Resumability (Qwik): the server serialises into the HTML the signal graph, the subscriptions, and pointers to every handler ("this button's click lives in chunk X, function Y, with this captured state"). The client executes nothing upfront — the first interaction lazily loads just the handler it needs and continues. The price: everything crossing a lazy-load boundary must be serialisable, which is what Qwik's $ optimizer enforces.

Why it matters for us: everyone except Qwik serialises only values and rebuilds the graph client-side — that is our v1 SSR design (§7). Qwik is the proof that serialising the live graph is possible; if the R31/R42 compiler ever targets it, this is the mechanism to study.

Svelte 5 runes

руны — это макросы компилятора: $-функции, которые превращаются в сигналы

Runes are compiler macros that look like functions: $state(), $derived(), $effect(), $props(). They are not imported and don't exist at runtime — the Svelte compiler sees them and rewrites your plain-looking code into signal operations:

let count = $state(0);            // becomes a signal source
let double = $derived(count * 2); // becomes a lazy computed
$effect(() => console.log(double)); // becomes an effect

count += 1;                        // compiles to a signal write

$state on an object/array installs a deep proxy (one lazy signal per property); plain variable reads/writes compile to .get()/.set(). That's why the code looks like ordinary JavaScript with no .value — the compiler put the reactivity there. The limits come from the same trick: it only works inside files the compiler processes, and a bare exported let loses reactivity at the module boundary.

Why it matters for us: runes are the strongest existing proof of our "disappearing framework" thesis (F2, R23, R42): familiar-looking code, compiler injects the reactive machinery at the boundaries. Our compiler aims at the same ergonomics for store code — across frameworks, not inside one.

Signals vs streams — and operator fusion

сигналы = состояние (pull), стримы = события во времени (push); fusion — склейка цепочек операторов

A signal holds current state: the graph knows its dependencies, guarantees a consistent view, recomputes lazily. An observable stream pushes discrete events through operator chains: dependencies are wired by hand (combineLatest), there is no glitch-freedom (a diamond over combineLatest emits intermediate pairs), but time operators (debounce, retry, buffering) are unmatched. The standards reflect the split: TC39 Signals for state, WICG Observable for events. Rule of thumb: state lives in signals; event streams feed transactions.

Operator fusion — most.js's famous optimisation: .map(f).map(g) collapses into .map(x => g(f(x))) at composition time — one pass, no intermediate allocations. RxJS never fused automatically; most.js proved the win. For us this is a compiler pass, not a runtime trick: chains of derive and derive.collection(filter → map → sort) pipelines fuse statically into single passes (decision D-rxjs).

Why it matters for us: the rx source adapts Observable<ChangeBatch> into collection transactions (§8.4); RxJS also earns a row in the reactivity comparison (R27) so the push-vs-pull trade-off is shown, not asserted.

ElectricSQL shapes — realtime over plain HTTP

шейп = подписка на срез таблицы как resumable HTTP-лог с оффсетом

A shape is a subscription to a slice of a Postgres table (table + where + columns) delivered as an append-only log over plain HTTP GET: the client asks /v1/shape?offset=…, gets changes since that offset, and long-polls (or SSE) for more. Because it's just cacheable GETs, there is no stateful socket tier — a CDN can fan one shape out to thousands of clients; after offline, a client resumes from its stored offset — nothing is missed, nothing is duplicated. Writes stay in your own API; Electric only solves the read path.

Pains it removes: hand-written cache invalidation ("when X changes, refetch Y"), websocket infrastructure and reconnect logic, thundering-herd refetches, lost-update windows after reconnect. Why it fits agent workloads (their own positioning): dozens of agents polling the same state become one CDN-cached log; each agent process can die and resume from its offset with a consistent view.

Why it matters for us: beyond the electric source adapter — the pattern (resumable offset log per subscription slice) is worth copying for Hyper itself and for the code factory (rig+lmao/axe): task state, worktree status, and review queues consumed by many agents are exactly "shapes"; the orchestrator becomes a log server, and agents become resumable subscribers (R50). Same idea already powers our remote protocol's resync(fromSeq).

LiveStore's git-like sync (pull → rebase → push)

клиентские события ребейзятся поверх серверного лога — как ветка поверх main

LiveStore keeps state as an event log (past-tense, versioned events; state = fold of the log). Sync works exactly like a git branch: the backend holds the authoritative, totally-ordered log (main); your device accumulates local events (your branch) — offline included. On (re)connect: pull new upstream events, rebase your pending local events on top of them (re-apply after, materialised state recomputed through pure fold functions), push; if the server accepted someone else's events first, you pull-rebase again. Undo is a compensating event (like git revert), which stays correct under concurrent edits — you never rewrite shared history.

Why it matters for us: we already took the hygiene rules (§4.6: versioned past-tense events, clientOnly vs synced, compensating undo §4.10). The pull-rebase-push loop is the reference design for R47 offline accumulation — and note it is the same shape as Zero's mutator rebase and our optimistic overlay (§4.11): three systems, one idea — local intent replayed on top of authoritative truth.

redux-form post-mortem (draft, R48)

почему было медленно — по причинам, и что из этого мы уже сняли

Why it was slow and painful, cause by cause: (1) every keystroke dispatched an action into the single root store, and every connected component's mapStateToProps re-ran — cost proportional to app size, not to the one input; (2) the form state lived as one nested object, so each keystroke rebuilt the whole form subtree (no per-field granularity); (3) validation ran synchronously on the whole form per keystroke; (4) action log noise (CHANGE × every character) drowned devtools; (5) serialisation pressure — the whole form state was JSON-ready at all times, even transient focus/touched flags.

Point-by-point in our design: per-field signals mean a keystroke notifies exactly one input's subscriber (§4.9); transient transactions are coalesced per frame and excluded from the command log (no devtools noise, no log growth); validation is per-field and compile-time-generated (R49/typia); persistence excludes transients by default. The principle stays ("all state global"); the mechanism that made it expensive is gone. Full write-up with measurements: R48, pending.
