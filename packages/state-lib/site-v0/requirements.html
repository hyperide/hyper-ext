Requirements — canonical list

Consolidated from Mextner's braindumps and decisions (2026-09-01 → 2026-09-03), cleaned up and translated to English. This file is the source of truth for requirement IDs; the master spec traces to them. Status: spec = covered by master spec v0.3, partial = spec covers part, backlog = not yet in spec.

Product frame

  • F1. A universal state toolkit for any project's state — a new, opinionated, universal product, not a Hyper-internal library. Hyper (VS Code extension + SaaS sharing one React codebase) and apps users build in Hyper are the first customers and the acceptance test. (spec §1)
  • F2. Disappearing framework: a compiler specialises the library per project usage (Svelte-style); the bundle contains only what the project uses; a CLI scaffolds per project needs. (spec §5)
  • F3. Toolkit, not monolith: every capability is an optional, replaceable module; everything works well together and without any part, or with parts swapped for what a project already uses. (spec §1, §3)

Ergonomics

  • R1. Global store as convenient as local React hooks; no selectors or manual memoization in the common case. Redux's real pain was not boilerplate but constant memoization — easy bugs, slow, memory-hungry. (spec §4.3)
  • R2. Mutable-looking writes over immutable, structurally shared snapshots. (spec §4.2, §4.4)
  • R3. Colocation and reuse: state + logic + UI decomposable per page and per reusable "HOX" (high-order compleXes: reducers + selectors + actions + adapters/providers + widgets for a reused UI part — Mextner's Redux-era invention); sliceable into hooks; no _.get(state,'a.b.c'). Hooks proved that uniting ui+state+logic enables easy decomposition; reducers/thunks implicitly relying on state made them hard to test and detached logic from components. (spec §4.8)
  • R4. Per-item updates in items.map(<Card/>) / <For> without re-running the loop. (spec §4.5, §6.1)
  • R5. Familiar, invisible, universal, fast — no Solid-style special utilities (e.g. prop-splitting) required of the user. (spec §5, §6)

Model

  • R6. All state global — including pure UI state and per-keystroke form state. redux-form was a mistake of mechanism, not principle: the mechanism must make this free. (spec §4.9)
  • R7. Events for all changes (Danny's requirement). Event sourcing + FSM are the useful concepts inside Redux. (spec §4.4, §4.6)
  • R8. Signals as the reactivity primitive. (spec §4.1)
  • R9. Structural sharing; memory-conscious. (spec §4.4)
  • R10. Undo/redo and optimistic updates as toolkit features. (spec §4.10, §4.11)

Data / middleware toolkit

  • R11. Pluggable data-source middlewares with auto-sync: REST, GraphQL, RPC (incl. VS Code postMessage), WebSockets/SSE, RxJS, CRDT, TanStack; combinable heterogeneous sources. (spec §8)
  • R12. Local persistence with filtering of what persists (IndexedDB etc.). (spec §8.5)
  • R13. Browser history / routing / URL query as store-backed state. (spec §8.6)
  • R14. Middlewares (and core where it pays) may use wasm, web workers, service workers. Decision so far: core stays pure JS; wasm only in CRDT/SQLite plugins inside the worker host. (spec §8.8, §9.3)

Engineering qualities

  • R15. Easy unit tests for dumb components; per-test store instances. (spec §12.1)
  • R16. Easy debugging of user problems — reproducible event logs, recordings. (spec §11.4)
  • R17. Easy Storybook stories. (spec §12.2)
  • R18. Clean separation: UI / UI logic / business logic. (spec §4.8, §17)
  • R19. Framework-agnostic core; adapters for React/Vue/Solid/Svelte/web components; works with SSR, server components, meta-frameworks (front+back in one framework). (spec §6, §7)
  • R20. Zero dependencies, tiny bundle, ESM, tree-shaking; "faster than vanilla JS" as aspiration, measured bars as the enforceable form. Old browsers can be dropped. (spec §13, §14)
  • R21. Devtools that are pleasant and never freeze — unlike Redux DevTools' UI. (spec §10)
  • R22. Modern browsers only. (spec §13)

Compiler, CLI, tooling

  • R23. Compiler ("disappearing framework"): per-project specialisation; all React integration modes available, selected per component; event-logging mode per slice. (spec §5)
  • R24. state-cli: init (interactive scaffolding), migrate, build (compiler), doctor, bench. (spec §11.2)
  • R25. Agent tooling (MCP): search/edit of state definitions, dumping states from a backend into fixtures, generating dev-server mocks from snapshots and recorded event logs. (spec §11.3)
  • R26. state.config.yaml records the approach chosen at state init as explicit invariants; state lint guarantees the project uses that one approach (no conflicting or bundle-bloating mixes); state migrate is the fix/normaliser. Invariants change only by explicit edits. (spec §5.1, §11.2)

  • R29 (backlog). Runtime type checking section and integration: survey the new generation of validators that are many times faster than zod/ajv (candidates to verify: ArkType's JIT set-theory engine, typia's compile-time codegen, TypeBox/valibot), pick the story for validating at collection/action boundaries, and compare honestly.
  • R30 (partial — spec §11.2). state migrate must migrate code from other libraries and approaches to our system, ≥80% automated via AST/LSP, targeting the project's chosen usage variant; whole-project or piece-by-piece; must also switch between our own usage shapes (hooks ↔ multiple stores ↔ single store); must analyse the repository to help choose the target configuration; every migration offers an optional LLM post-processing step to finish what AST rules could not.
  • R31 (backlog — separate utility, not inside state-cli). A compile-React tool inspired by (and compared against) React Compiler, which "only removes useMemo" — we should aim higher: optionally compile React code into something Solid-/Qwik-like and super-optimised, with optional runtime type checks injected; components keep using useState while the compiler turns it into global state under the hood — giving full-state testing, user-problem debugging, recordings, and the rest of the global-state benefits without changing component code.
  • R32 (backlog). Danny's database as the query layer: a Datomic-like DB written in Rust compiled to wasm, with a powerful query language. Complex derived state moves from hand-written, slow, test-heavy selectors into declarative queries against it.   • R33 (backlog). Assess Hyper-side benefits before/while migrating: which whole classes of Hyper bugs the new state engine eliminates; whether it gives the right path to collaborative editing; indexing all code and worktrees; fast editing/navigation; blast-radius view; possible benefits for the style-editing-core master spec.

  • R37 (backlog). state cli implemented in Python, in the style of the rig ecosystem tools. (Tension to resolve: the analyzer/compiler must live in TypeScript to use the TS compiler API — the likely shape is a Python CLI/TUI shell in rig style driving a TS analyzer service; see DECISIONS.)

Decision changes (2026-09-03)

  • D-react-mode. React tracked mode (useSignals-style render tracking) should be opt-out, not opt-in: enabled by default and recommended instead of React Compiler, since our compiler + fine-grained subscriptions aim to make React Compiler unnecessary. Snapshot mode remains the automatic fallback where React Compiler is detected and active. (Supersedes the v0.2 "snapshot is the only inferred mode" default; the config invariant records the choice per project.)
  • D-zustand. Zustand is upgraded from "context/superseded" to a primary competitor deserving deep comparison: it has many strong ideas and APIs and many usage variants (actions in the store or not, direct writes vs actions, slices, vanilla, middlewares) — the comparison must cover its variants, not one caricature.
  • D-rxjs. RxJS is not only an API-layer item: compare it as a reactivity system too (push streams vs pull signals), and study operator fusion (e.g. most.js merging consecutive maps into one) as an optimisation our compiler should apply to derived chains.
  • D-legend. Legend-State's fine-grained React primitives deserve a feature-level comparison against Solid and others (are they more convenient/faster?), not just a "watch" verdict.

Confirmed formulations

  • Redux ≈ event sourcing + FSM: yes, with nuance — actions are events and the state is their fold (event-sourcing shape), but the events are not the persisted source of truth and reducers are transition functions without explicit states/guards (implicit FSM). Our design makes both aspects explicit and optional: the command/patch logs are real logs, and fsm() is a real state machine.

Added 2026-09-03 (second batch)

  • R40 (spec update pending). state migrate gets subcommands, not one command with every option: the described scenarios are entirely different migrations — migrate from <lib> (other library/approach → ours), migrate shape <hooks|multi-store|single-store>, migrate slice <name> --sync <a>→<b> (e.g. auto DB sync → manual handlers), migrate mode (react mode / events mode changes), each with --analyze, partial scope, and the optional --llm post-process step.
  • R41. The push-pull reactivity core must exist as an isolated, pure, well-tested dependency. If no library offers that shape (alien-signals is isolated and pure but carries modest test coverage), we publish our own standalone package with a serious test suite. Additionally: benchmark the implementation variants against each other — linked lists vs arrays for dependency storage, dirty flags vs version counters — and either pick the winner or make the variant switchable (statically per build, possibly dynamically per workload) behind the same interface.
  • R42 (extends R31). Our own TS/React compiler direction: an agnostic version plus variants for any JSX and for specific rendering engines (React first). It must understand where reactive boundaries are crossed and inject the required code automatically, so application code looks completely familiar — deep-proxy ergonomics without manual wiring (no special utilities, per R5).
  • R43 (research). wasm state research: can the whole state live in wasm memory — shared memory (SharedArrayBuffer/threads), zero-copy or copy-avoiding schemes, layouts that exploit our immutability/structural sharing; alternatively invent algorithms that give deep-proxy ergonomics without Proxy overhead, or rethink the approach to avoid Proxy entirely. Compile-target variants: js and wasm builds of the core (R46).
  • R44. state build should also optimise: simplify generated code, reduce deoptimisations (hidden-class stability, monomorphism), use asm.js-style patterns where they help, and emit performance hints for developers/agents; where transpilation alone cannot achieve an optimisation, state migrate applies it as a refactor.
  • R45. Devtools name fidelity: React DevTools notoriously fails to show hook names (even the "parse hook names" button usually fails). In our devtools names and internal values must always resolve — with zero runtime overhead, via a separate build-time metadata file ("devtools maps", analogous to source maps) shipped next to the bundle.
  • R46. Compile-target variants: js and wasm outputs of the core (see R43).
  • R47 (research section). Offline-first collaboration: the concrete pattern for working without internet, accumulating local edits, and syncing to the backend when connectivity returns — as its own section alongside collaborativity, CRDTs and adjacent approaches (relates to spec §8.7 outbox and §4.11, but needs the full comparative treatment).
  • R48 (research). redux-form post-mortem: analyse in detail why exactly it was slow and inconvenient, and document point-by-point how our design avoids each cause.
  • R49 (decision). typia-style compile-time validation is adopted as the default validation story in our compiler (validators generated from TS types at build time, zero runtime schema cost); runtime schema libraries (zod/ArkType/valibot) remain supported via Standard Schema for interop.
  • R50 (research). ElectricSQL ideas beyond the state toolkit: evaluate its resumable-shape-log model for Hyper itself and for the code factory inside Hyper (today the rig+lmao/axe ecosystem) and the agent-orchestration system — they position it for agent workloads.
  • R51 (matrix conventions). The comparison matrix may assign multiple verdict badges per row with per-badge notes (e.g. "steal ideas" + "interop"); PouchDB/CouchDB is reclassified as context; the API layer vs Transport & tooling split needs clearer layer descriptions (API layer = how the app talks to backends: typed requests, caches, subscriptions; Transport & tooling = the plumbing and DX around our own modules: message bridges, URL state, undo helpers, devtools hosts).
  • R52. Immutable.js is not fully discarded: mine and possibly improve its ideas (HAMT node design; it can beat Immer when staying inside its structures and skipping toJS); likewise structura.js ideas (compile-time freezing via readonly types, circular/multi-reference support, moves/transpositions inside drafts) are candidate features.
