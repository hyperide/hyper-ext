State Management Research Brief

Scope: a state layer for Hyper (VS Code extension + SaaS sharing one React codebase) and for the apps users build inside Hyper (Next.js / Remix / Vite / Bun templates). Status: research phase complete → this brief → briefing session → master spec + full competitor matrix + build-setup fit check. Date: 2026-09-01. All versions, sizes and dates below were verified against npm / project docs on this date. Sizes are min+gzip of the whole package unless noted.

0. TL;DR

  1. The reactivity algorithm is solved; don't reinvent it. alien-signals, Preact Signals, Svelte 5, Solid 2, Vue 3.6, Angular and the TC39 proposal all converge on the same push-pull, three-state (clean/check/dirty), lazy-computed, auto-tracking design. alien-signals is 1.9 kB / 0 deps and exposes createReactiveSystem() for custom node types. Wrap it behind a 5-function internal interface so it can be swapped for native Signal later. Do not build on signal-polyfill (Stage 1 since 2024, "not for production", no batch/effect).
  2. "No selectors, no memoization" collides with the React Compiler. Every library that gives hooks-like ergonomics without selectors tracks reads during render (Valtio useSnapshot, MobX observer, Legend observer, Preact useSignals, tldraw track). React Compiler v1 (Oct 2025) memoizes on reference identity and its lint flags this pattern as "interior mutability"; Preact's babel transform already conflicts with it. The compiler-safe contract is: hook returns a new immutable snapshot reference when the read slice changes (uSES style), and fine-grainedness lives in the subscription (per-property signals under a proxy, subscribe only to paths read in the last render). Keep render-time proxy tracking as an opt-in ergonomic layer, not the foundation.
  3. "Every change is an event" and "mutable proxy ergonomics" are compatible if the store treats a mutation as a transaction that emits patches (Immer/Mutative-style JSON patches + inverse patches). Commands (intent, named + args) go in one log, patches (effect) in another. That single decision gives undo/redo, devtools time-travel, cross-webview replication, persistence deltas and sync outbox for free.
  4. The data layer already exists: TanStack DB (0.8.7, MIT, still beta). Its collection-options contract (sync(begin/write/commit/markReady) + onInsert/onUpdate/onDelete + utils), two-store model (synced truth + optimistic overlay, rebased on confirmation), differential-dataflow live queries, and @tanstack/offline-transactions outbox are exactly the middleware design described in the braindump. Either adopt it or copy its contract; don't design a third one.
  5. Hyper's codebase already runs a leader/replica store (StateHub in the extension host broadcasting SharedEditorState patches to panels, with a hand-written race fix in mergeInitState). The new core should formalise that: patch-based replication with sequence numbers, transport drivers for VS Code postMessage / BroadcastChannel / MessagePort / chrome.runtime.
  6. Things in the braindump that reality pushes back on: "faster than vanilla JS" (only Legend-State claims it, on krausest swap/replace rows, in beta); wasm for structural sharing (no evidence it beats V8 for object graphs once marshaling is paid — wasm belongs to CRDT/SQLite plugins only); Proxy get is ~13× slower than plain property access on current V8, so proxies stay off hot loops and need snapshot()/toRaw() escapes; per-item list updates in React bottom out at component granularity (no mapArray equivalent); uSES-driven updates are always synchronous (never time-sliced).
  7. Preliminary recommendation: build a small own core (~4–6 kB) = alien-signals-class algorithm + lazy per-property proxy store + patch-emitting transactions + keyed collections, with a first-class adapter contract copied from TanStack DB; ship React/Vue/Solid/Svelte bindings as ~10-line uSES / from() / createSubscriber / shallowRef bridges; reuse existing libraries for the periphery (TanStack DB or its contract for server collections, nuqs/TanStack Router for URL, Dexie/IndexedDB persister, birpc/vscode-messenger transport, TanStack Devtools shell + Redux DevTools bridge). Details in §6; open questions in §7.

What this tells us

  • There are at least four state mechanisms coexisting (local hooks, Zustand stores, StateHub replica, canvas-engine) plus a fifth (TanStack Query) barely used. The pain is not any one of them; it is that data fetching, RPC, cross-panel sync, persistence and undo are each solved locally, per hook, with no shared event stream.
  • The leader/replica topology is already the right shape for VS Code (extension host = leader, webviews = replicas). It just lacks sequence numbers, patch semantics, buffering while a webview is hidden, and a transport interface — hence the race hack.
  • The PlatformMessage union is effectively an untyped-at-runtime RPC protocol. It is a good candidate for the transport driver layer ({post, onMessage}), not something the new store should replace wholesale.
  • 278 useState + 329 useEffect is the "hooks abstracting REST/RPC" problem in numbers: each is a private cache with private loading/error state that devtools, tests and Storybook cannot see.

2. Requirements (normalised from the braindump)

Numbered so the master spec can reference them.

Ergonomics - R1. Global store as convenient as local React hooks; no selectors or manual memoization in the common case. - R2. Mutable-looking writes (store.user.name = 'x', items.push(...)) with immutable, structurally shared snapshots underneath. - R3. Colocation: state + logic + UI decomposable per page / per reusable "HOX" (reducers + selectors + actions + adapters + widgets), reusable and sliceable into hooks; no _.get(state, 'a.b.c'). - R4. Per-item updates in items.map(<Card/>) / <For> without re-running the loop. - R5. Familiar, invisible, universal — no Solid-style prop-splitting utilities required.

Model - R6. All state global — including pure UI state and per-keystroke form state (while acknowledging redux-form was a mistake: the mechanism must be cheap enough that this is not a regression). - R7. Every change is an event (Danny). Event sourcing + FSM concepts retained from Redux. - R8. Signals as the reactivity primitive. - R9. Structural sharing; memory-conscious. - R10. Undo/redo and optimistic updates as toolkit features, not app code.

Data / middleware toolkit (all optional, all interoperable, all replaceable) - R11. Auto-sync with backends via pluggable data-source middlewares: REST, GraphQL, RPC (incl. VS Code postMessage), WebSockets/SSE, RxJS, CRDT, TanStack. - R12. Local persistence with filtering of what persists (IndexedDB etc.). - R13. Browser history / routing / URL query as store-backed state. - R14. Middlewares may use Web Workers, Service Workers, wasm where it pays.

Engineering qualities - R15. Easy unit tests for dumb components; per-test store instances. - R16. Easy debugging of user problems (reproducible event logs). - R17. Easy Storybook stories. - R18. Clean separation UI / UI logic / business logic. - R19. Framework-agnostic core; adapters for React, Vue, Solid, Svelte, web components; works with SSR, RSC, meta-frameworks. - R20. Zero dependencies, tiny ESM, tree-shakable, subpath exports; "faster than vanilla" as an aspiration, "never slower than Zustand/Valtio" as the bar. - R21. Devtools that do not freeze and are not "the Redux DevTools UI". - R22. Old browsers not supported (Proxy, ES2022+, OPFS/Web Locks may be assumed where present).

Two audiences: Hyper itself (webviews + SaaS, React 18 today) and user apps generated by Hyper (Next.js/Remix/Vite/Bun templates with shadcn/tamagui → SSR/RSC are concrete, not theoretical).

Insights - Sync, glitch-free reads + batched notification to frameworks is the scheduling split that "feels like useState" (Preact/Vue/alien). Solid 2 / Svelte 5 microtask batching requires flush() for sync reads — unfamiliar for React devs (R5). - Deep proxies create one signal per property lazily on first tracked read (Svelte, Solid, Vue, MobX, deepsignal), so an untouched 50 k-row table costs nothing. Known gotchas to design around: class instances / Map / Set / Date need wrappers; destructuring loses reactivity; proxy vs raw identity (toRaw/unwrap/$state.snapshot); array length as its own signal. - R4 (per-item list updates) exists at two layers. View layer: Solid mapArray/<For>, Svelte keyed each, Lit watch(). React has no equivalent — the practical floor is component-level: parent subscribes to the ordered id list only, each <Card id> subscribes to its own row signal; with TanStack Virtual, rows subscribe independently. Store layer: signia's getDiffSince/withDiff and Solid 2 createProjection + keyed reconcile are the only "derived list without re-running the loop" mechanisms; a derived-collection API in our store must be diff-aware. - SSR: only Qwik serialises a live signal graph; everyone else serialises raw values and rebuilds computeds on the client. Snapshot the raw tree, never proxies; per-request store instances.

Insights - Immer 11 (Nov 2025 rewrite) closed most of the gap to Mutative (+21–26 % avg, up to 59 % on update-reuse) but still defaults to auto-freeze, which dominates cost on big trees; RTK measured 37–408× slowdowns on 10 k-item arrays before fixes. Mutative's "10×" holds only with freeze off. Copy-on-write proxies are O(size of touched container); >10 k hot arrays should be normalised (ids + byId) — which R4 wants anyway. No mainstream store ships a HAMT backend; not needed. - Event log for free today: XState v5 / @xstate/store (typed inspection events), RTK (by design), Effector (inspect with causal chain), mobx-keystone (serialisable actions + patches). Reatom's cause tracking (every update records why) is the best debugging idea in the field (R16). None combine this with proxy ergonomics — that gap is the product opportunity. - statebus (Danny) is a proof of concept of the right architecture: typed States/Events augmentation, rAF-drained double-buffered queue, all reducers then all listeners, ByID<T> lazy atom maps, substateInterest ref-counting so providers fetch on demand, useBus() Proxy for typed publish. Gaps: reducers' README vs types disagree, no middleware despite the diagram, no log/replay/undo/persistence/devtools/test helpers, exact react@18.3.0 peer, site DNS dead. Worth keeping: the interest-counting idea (lazy connect/disconnect of data sources per key) and the phase ordering. - Best per-test isolation: Effector fork() (overrides values and effect handlers), then Jotai/Zustand-vanilla/xstate factories. Module-level singletons (default Zustand create, Legend globals) are what break Storybook and SSR (R15, R17, R19). - Devtools: Redux DevTools serialises whole state per action across a process boundary → freezes (#282, #619, zustand #926); Pinia had the same failure (#721). Jotai devtools 0.14 and Stately Inspector are the current best; TanStack Devtools (alpha) is a framework-agnostic shell with a Vite plugin that strips to zero bytes in production — a good host for our panel.

Patterns worth stealing (each maps to a toolkit middleware) 1. Two-store split — immutable synced truth + optimistic overlay, rebased when truth changes, dropped on confirmation (TanStack DB, Electric "shared persistent optimistic state", Zero). Rows expose $synced/$origin. 2. Adapter contract = sync({begin, write, commit, markReady, markError}) + onInsert/onUpdate/onDelete + source utils; rule: subscribe to the live channel before the initial fetch and buffer. Fits REST polling, GraphQL subscriptions (graphql-ws), WebSocket, RxJS and VS Code RPC identically (R11). 3. Handlers resolve only after sync-back (Electric txid, RxDB awaitInSync, Zero ack) — otherwise the UI flickers. Our RPC must return a monotonic version the store can await. 4. Intent-based mutators (Zero/Replicache): ship name + validated args, rerun on server, natural command log for undo/replay/idempotent retry (R7, R10). 5. Outbox before dispatch: persist to IndexedDB first, FIFO, backoff + jitter, NonRetriableError, idempotency keys, leader election via Web Locks (@tanstack/offline-transactions is small enough to copy). Background Sync API is Chromium-only, so the queue must live in-app. 6. Event-sourcing hygiene (LiveStore): past-tense versioned event names, never delete an event definition, pure materialisers, clientOnly vs synced events, soft deletes, globally unique ids; undo = inverse event (sound under concurrent remote edits; snapshot undo is sound only for local-only state). 7. Origin-scoped undo (Yjs trackedOrigins, Loro excludeOriginPrefixes, mergeInterval ~500–1000 ms, onPush captures selection). 8. Incremental view maintenance — derived collections consume ChangeMessage[] deltas, not snapshots (TanStack DB createEffect enter/exit/update; Zero IVM). 9. Persistence as per-collection policy — what / where / transform / TTL / buster / version+migrate (Zustand partialize, Query shouldDehydrateQuery, TinyBase subsets, Legend synced({persist})) (R12). 10. Storage spectrum — localStorage → IndexedDB (Dexie 4.4, multi-tab safe) → SQLite wasm on OPFS (fast; needs worker + COOP/COEP or single-connection sahpool + leader election). Keep the persister interface storage-agnostic so the VS Code webview and SaaS can differ. 11. URL as a persister — nuqs 2.10 (Next, React Router 6–8, TanStack Router), TanStack Router validateSearch (Standard Schema, retainSearchParams/stripSearchParams), Reatom withSearchParamsPersist, jotai-location atomWithLocation with updateFromSource to avoid router cycles (R13). 12. Transport — birpc 4.2 (~0.5 kB, needs only post/on) or penpal 8; not Comlink (VS Code postMessage cannot transfer MessagePort, discussion #2392). oRPC 1.15 has a MessagePort adapter; tRPC 11 has SSE subscriptions with tracked() resumption — one typed contract can serve SaaS (HTTP/SSE) and extension (MessagePort). vscode-messenger 0.6.1 gives typed request/notification + broadcast + diagnostics. 13. Sync engine in a worker (LiveStore SharedWorker leader, PowerSync, TanStack DB persistence). SharedWorker is missing on Chrome Android → Worker + leader election fallback. Design the core transport-agnostic so the same engine runs in a worker, the extension host, or the page (R14).

3.4 Integration: React, other frameworks, SSR/RSC, VS Code, devtools, workers, bundling

React - useSyncExternalStore: updates are rendered synchronously even inside startTransition (RFC 0214) — store updates never time-slice. getSnapshot must return a cached reference; getServerSnapshot is mandatory for hydration. A PR to add proxy access-tracking to useSyncExternalStoreWithSelector (react #32040) was closed stale in June 2025. - React 19: use(promise) needs a cached promise per key; useOptimistic / actions are React-local — the store should expose "apply optimistic patch / reconcile on settle" rather than own that layer; <Activity> keeps hidden subtrees subscribed, so "subscribed ≠ visible". - React Compiler v1: memoises on reference identity; MobX observer, TanStack Table v8, Preact transform all documented as breaking. Escape hatches ("use no memo") are debt. With the compiler on, inline selectors become cheap — the cost argument against selectors weakens, the correctness requirement (stable snapshot refs) stays. Hyper does not use the compiler yet; user apps on Next.js will. - Per-item lists: parent subscribes to id list; <Item id> subscribes to store.get(id); flame graphs show one component reconciling instead of the list.

Vue / Solid / Svelte / Angular / Lit / Qwik - Vue: shallowRef + subscribe → assign snapshot (triggerRef for in-place); build against the public surface, not internals (3.6 swapped them). Pinia = per-app container, devalue serialisation, restore before first useStore(). - Solid: from(subscribable) → signal; object graphs via setStore(reconcile(next, {key:'id'})). - Svelte 5: createSubscriber(start) from svelte/reactivity (≥5.7) + $state.raw; module-level $state exports are frozen at import; SvelteKit forbids shared mutable server state. - Angular 22: zoneless + OnPush default; toSignal/toObservable at boundaries; @ngrx/signals is the convention. - Lit: @lit-labs/signals binds to the TC39 polyfill — one copy per page or the graph partitions; cross-shadow-root sharing via the Context Community Protocol (context-request event), implemented by @lit/context. - Qwik: only serialisable data crosses $ boundaries; a store instance is not portable — expose snapshot + id-based re-attach.

SSR / RSC / meta-frameworks (concrete for Hyper's Next.js / Remix templates) - Universal doctrine: no module-level store; createStore() factory in a Provider created once per tree; RSC never reads/writes the store; per-request QueryClient-style scoping (cache()), HydrationBoundary per route, shouldDehydrateQuery incl. pending promises (streaming), serializeData/deserializeData for non-JSON; derived state recomputed on the client, not serialised. - Effector fork/serialize/hydrate (needs SIDs via babel/SWC), Reatom ctx, Jotai Provider + useHydrateAtoms, Zustand Next.js guide — all the same pattern. - Streaming SSR: stores must not mutate during render; hydrate before first subscription. Astro islands: nanostores, client-only.

VS Code webview - postMessage is JSON-serialisable data; ArrayBuffer transfer exists (#115807) but zero-copy is impossible remotely and MessagePort transfer does not work. Design for JSON + optional binary blobs. - Without retainContextWhenHidden the webview is destroyed when hidden and messages are lost; getState/setState (+ WebviewPanelSerializer) is the sanctioned persistence. @vscode/webview-ui-toolkit is deprecated (Jan 2025). - Extension host = leader, webviews = replicas receiving patches; buffer while hidden, replay on onDidChangeViewState; resync from sequence number on reconnect. Browser-extension analogues: webext-redux, webext-bridge.

Devtools - Non-freezing design: log events/patches, not snapshots; time travel = replay patches; lazy serialisation on inspect (send handles/paths); filter/sampling for high-frequency events; diff in a Worker; virtualised tree; cap history by bytes; versioned protocol. window.devtoolsFormatters (Chrome + Firefox) is a cheap win for console inspection of proxies/atoms. Ship a TanStack Devtools plugin plus a Redux DevTools bridge (familiarity) with maxAge + sanitisers by default.

Workers / wasm / service workers - postMessage cost scales with payload: ≤10 KiB fits a 16 ms frame on slow phones — send patches, chunk big patch sets, transfer ArrayBuffers. Structured clone rejects Proxies (DataCloneError) — snapshot before crossing. - SharedArrayBuffer/wasm threads need COOP/COEP (Chrome 137 adds Document-Isolation-Policy; Firefox/Safari still need both) — deployment friction a state library should not impose. - wasm: no general-purpose wasm state manager exists; CRDTs are the wasm players (Loro 894 kB gz, Automerge 591 kB gz vs Yjs 25 kB gz; parse times dominated by the JS↔wasm boundary). Mutative in plain JS does 6,783 ops/s with patches. Keep the core single-threaded pure JS; wasm and SQLite are plugin boundaries.

Bundling / Proxy performance - "Tiny, zero-dep, tree-shakable" concretely: "type":"module", ESM-only, "sideEffects":false, subpath exports per adapter (jotai/react, tinybase/persisters/*), /*#__PURE__*/ on factories, size-limit CI (nanostores gates atom at 372 B). - V8 Proxy costs (2026 re-run): get ~13×, set ~27×, has ~7×, ownKeys ~89× vs plain access. Keep traps monomorphic (one handler object), never ownKeys/spread proxies in hot paths, cache proxies per target in a WeakMap, always offer snapshot()/toRaw(). Draft-style proxies (Mutative) pay the cost only inside the mutation window — which is why "mutate inside a transaction, read plain snapshots outside" is the fast shape.

5. Tensions the spec must resolve (braindump vs reality)

  1. "No selectors" vs React Compiler. Decide: snapshot-returning hooks with fine-grained subscriptions (compiler-safe, default) + optional render-time proxy tracking behind an explicit flag and lint rule. This is the single most consequential design decision.
  2. "All state global, even per keystroke" vs input semantics. Technically fine with per-property signals + component-level subscription (a keystroke updates one signal → one <Input> re-renders); but controlled inputs in React 18 need the write to be synchronous within the event to avoid caret jumps and IME breakage — uSES's sync semantics actually help here. Cost lives in the event log and persistence middlewares, not the store: they must debounce/coalesce (mergeInterval), mark keystroke transactions as clientOnly/non-persisted by default, and undo must group them. Redux-form failed on mechanism (top-level re-render per keystroke + serialisation), not on the principle.
  3. "Events for everything" vs "mutable writes". Resolved by transactions emitting patches; but decide the granularity of the command: is store.user.name = 'x' outside a named action an anonymous command (allowed, logged as set /user/name) or an error in strict mode (MobX enforceActions style)?
  4. "Faster than vanilla." Not a goal a store can meet in general; adopt measurable bars instead: ≤ Zustand/Valtio on js-reactivity-benchmark scenarios, krausest "swap/replace rows" parity with Legend, zero allocations on untouched subtrees, ≤10 KiB patch batches over postMessage.
  5. Framework-agnostic vs "familiar and invisible". The core can be agnostic; the ergonomic layer is per framework (React hook that returns snapshots; Solid that returns store proxies; Svelte via createSubscriber). Accept that the API surface will differ slightly per framework rather than force Solid-style utilities on React devs (R5).
  6. wasm / workers. Core stays pure JS single-thread; a worker host is an optional middleware; wasm only via CRDT/SQLite plugins. Anything else is scope creep.
  7. Adopt vs build for the data layer. TanStack DB is beta, large, and React-Query-shaped; but its contract is the right one and it ships 5 framework bindings + SSR. Options: (a) depend on it, (b) implement its collection contract natively in our core so its adapters (Electric, PowerSync, RxDB, Query) plug in, (c) ignore. (b) preserves R20 and interoperability.
  8. Backwards path for 145 hooks. The migration story must let a hook like useGitHubRepositories become a collection + live query in one step, with the rest of the app untouched — otherwise adoption stalls inside Hyper itself.

6. Candidate architectures

Option A — Assemble from existing libraries

alien-signals or @preact/signals-core (reactivity) + Mutative (patches) + @xstate/store or Valtio (store) + TanStack DB (server collections, outbox) + zundo-style history + nuqs (URL) + Dexie (persist) + birpc/vscode-messenger (transport) + Redux DevTools bridge. Pros: fastest to prototype; each piece maintained. Cons: three reactivity models (signals vs xstate-store vs TanStack DB's own store) that do not share a dependency graph → glue code, double subscriptions, no unified event stream; R20 lost (dozens of kB); R1 still needs selectors at the seams.

Option B — Own small core + adapters, borrow contracts (preliminary recommendation)

  • Core (~4–6 kB, 0 deps): push-pull signal graph (alien-signals-class; possibly vendored createReactiveSystem), lazy per-property proxy store (store.a.b.c reads track; writes only inside tx()/actions), transactions emit {txId, cause, command?, patches, inversePatches}; keyed collections (ids + byId) as a primitive; diff-aware derived collections (signia epochs or IVM-lite); snapshot()/toRaw(); factories only, no singletons.
  • Adapters (~10–40 lines each): React (uSES snapshot hook + optional tracked mode), Vue (shallowRef), Solid (from + reconcile), Svelte (createSubscriber), Angular (toSignal), Lit (Context Protocol + signals), SSR (dehydrate/hydrate, per-request scope via AsyncLocalStorage).
  • Toolkit middlewares (each a subpath export): history (patch-based, origin-scoped, mergeInterval), optimistic (overlay + rebase, handlers await sync-back), collections/* implementing the TanStack DB collection contract (REST/Query, GraphQL, RPC, WebSocket, RxJS, Electric, PowerSync, CRDT), outbox (IndexedDB, Web Locks leader), persist (per-collection policy; localStorage / IndexedDB / OPFS-SQLite / VS Code setState), url (nuqs-style parsers, router-aware), remote (patch replication over {post,onMessage}; drivers: VS Code, BroadcastChannel, MessagePort, chrome.runtime), worker host, devtools (event stream → TanStack Devtools panel + Redux bridge + devtoolsFormatters), fsm (xstate-store-like typed transitions on a slice).
  • Ergonomic layer per audience: Hyper: defineComplex() (HOX) = slice + actions + collections + adapters + widgets, mounted per page; user apps: same API, template presets for Next/Remix/Vite. Pros: meets R1–R21 by construction; one dependency graph → one event stream → one devtools; interoperable with the TanStack ecosystem via the contract. Cons: we own a reactivity runtime (mitigated: the algorithm is small and settled; vendoring alien-signals is ~600 lines); adapters × frameworks maintenance; needs a benchmark suite from day one.

Option C — Adopt TanStack DB + a signals lib, thin layer

TanStack DB for all server and most client data (local-only collections), a signals library for UI state, a thin defineComplex on top. Pros: least code, rides TanStack's SSR/devtools/framework work. Cons: beta with breaking minors; bundle far above R20; UI state and DB state still two worlds; no proxy ergonomics; no patch/event stream for UI state; devtools not ours.

Recommendation for the briefing: pursue B, prototyped in two weeks as a spike: core + React adapter + remote driver for VS Code + one collection (GitHub repositories via the TanStack DB contract) + devtools event stream, measured on js-reactivity-benchmark and krausest, and used to replace shared-editor-state + StateHub + useGitHubRepositories inside Hyper as the acceptance test. Keep A as the fallback if the spike misses the size/perf bars.
