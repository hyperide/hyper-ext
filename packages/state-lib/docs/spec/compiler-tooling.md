### Compiler, CLI and documentation contract

**Specification amendment.** Extends R23–R26, R34–R46, R54, R65–R66, R79–R84. The following keeps new requirements in their relevant system chapters rather than a detached ideas file.

Compile from the same TypeScript schema into accessors, relation metadata, validators, action contracts, form constraints, query plans and separate devtools maps. Use typia or an equivalent AOT generator before erasing types. Avoid Proxy on statically understood paths; a fallback is explicit and observable in explain/doctor output. The included checker-based transformer only proves static table/member paths and evaluation order, not a complete production compiler.

The CLI is the primary automation surface. State-definition search/edit, backend-to-fixture capture, snapshot/event-log mock generation and documentation search must be ordinary commands with machine-readable results. `state mcp` wraps the same command services; MCP must not hide exclusive functionality. Capture defaults to schema-driven redaction and excludes secrets. No backend credentials or unrestricted execution are embedded into the browser documentation examples.

Examples must show the same task, same fixtures and same output across compared APIs. Each executable snippet's button must run the code actually shown. A designed-only API is labelled; a snippet without an executable adapter must not pretend to run. The new operator corpus follows this contract for native JS and the experimental query algebra; jq/Ramda/Datalog/etc remain separately named adapter work. Concept references (including patch-emitting transactions and keyed collections) should link to explanations, not remain unexplained badges.

The API page reads the existing generated prototype metadata rather than inventing methods. Missing descriptions and truncated signatures are displayed honestly; completing documentation is not the same thing as enumerating entries. Spec additions are stored in `docs/spec` and composed into relevant chapters of the existing Master spec page, so the old markdown mirror remains unchanged and there is no hidden second copy of the additions.

#### Documentation UI acceptance criteria

Keep paired snippets inside two equal `minmax(0,1fr)` columns with independently scrollable code blocks and no overlap with the TOC. Show the complete selected corpus rather than hiding arbitrary cases behind a research-file reference. Each pair needs correspondence notes and, eventually, paired construct highlighting and value/type hints. The existing 22 production-selector corpus is distinct from the new 38-case executable operator corpus; migration of all older examples remains outstanding.

Header navigation needs delayed reset after genuine pointer leave, a re-entry grace period, edge-triggered smooth scrolling that can reach the final items, and an edge lens/3D effect disabled on the edge the pointer is exploring. Keyboard, coarse pointers and reduced-motion modes retain usable non-animated navigation. These behaviors are specified here but this revision does not claim to have rebuilt the menu.

The requirement destination table should use one explicit Req → Destination pair per row (or label two independent column groups visibly). Vector CLI diagram primitives belong to the separate vector tool: frames, tables, connectors/arrows and accessible color presets, plus an ASCII-box/arrow input format with an explicit supported grammar. This revision does not claim changes to an unavailable local `~/work/.../vecli.ts` checkout.

#### Generated projections and COW qualification — 2026-09-20

The [hybrid research report](../research/2026-09-20-cow-hybrid.md) documents the new Rust-generated projection boundary and the distinction between explicit application COW opt-in, compile-time module qualification and future per-command lowering. Generated modules are virtual, inspectable and source-mapped; ordinary raw/gzip and semantic-evidence gates still apply. This is not general arbitrary-callback compilation. COW historical-reference tests now pass, but whole-document promotion still fails required timing cells. The proposed combination is traced to sections 4.4/4.5/5 and primary persistence/ownership literature; it does not change the canonical contract to fit a benchmark.

#### Canonical identity of virtual generated modules — 2026-09-22

Generated ownership is keyed by the **resolved destination used by the bundler**, not the raw configuration spelling. Dot segments, contained parent segments and in-root directory symlinks cannot make two generating variants own the same destination. Authored roles use the same comparison, while ordinary containment and existing-file checks still apply. The [reproduction and regression record](../research/2026-09-22-generated-path-identity.md) covers six rejected alias cases plus distinct valid modules. Changes to this validator invalidate its existing source fingerprint; historical measurements remain historical. This strengthens the current projection preview without claiming immutable point/dense generation or whole-COW performance admission.

#### Declared immutable commands and bounded generated output — 2026-09-23

The Rust compiler recognizes a `json-command` declaration for scalar set/toggle, per-row/grouped scalar assignment (including sparse stride), move and no-op. It emits short calls into shared ownership-aware helpers, not a complete repeated engine for each command. A separate shared publication factory takes a dedicated Runtime, owns its disposal, and commits one coherent document/history value. The general callback adapter and declared commands use the same publication contract; applications that declare only commands need not import the arbitrary-draft Proxy implementation.

This is explicit command generation, not translation of unrestricted JavaScript callbacks or implicit selection of an arbitrary effectful mutation body. Atomic publication, original-root preservation, alias semantics, synchronous error/notification behavior and bounded history are conformance requirements. Dense array certificates and iterator checks are internal optimization facts, not trusted user declarations; sparse holes retain indexed-copy semantics.

The emitted-entry gate compares raw, gzip and Brotli bytes and accepts optional absolute `maxRawBytes`, `maxGzipBytes` and `maxBrotliBytes` limits. Absolute limits also constrain reference fallback; failure preserves previous output. The current scope is the actual emitted JavaScript entry graph and reachable imports, not a fictional function-only size or a completed multi-route/worker-asset audit.

The [command-builder record](../research/2026-09-23-command-builders.md) contains actual controller and growing-catalogue comparisons. Normal-workload median improvements do not hide failed tail/edge cells. The conservative admission rule is unchanged, so incomplete qualification still emits references. The [algorithm portfolio](algorithm-portfolio.md) records implemented candidates separately from prior-art proposals, and does not claim every surveyed structure has been implemented. Public marketing reports are paused; technical evidence remains available.

#### Shared native and browser compiler — 2026-09-24

`compiler/src/lib.rs` is the single Rust planner used by the CLI binary and browser Wasm export. The browser's `compile_json` boundary accepts bounded JSON source inventories and returns the same plan/generated modules; it never executes the supplied application. The host isolates compilation from the editable-program worker. Native qualification and full-entry size admission are not bypassed by publishing a workbench: the workbench explicitly compares both candidates and does not label its choice a production admission.

The profile fingerprint includes the shared planner and Cargo configuration. The [browser-compiler record](../research/2026-09-24-browser-compiler.md) documents exact parity tests and the separate library build target. Compiler and bundler artifacts are loaded on demand by the workbench and are accounted separately from the application entry they emit.

#### Fixed browser-entry specialization — 2026-10-16

`state build` accepts optional `buildConstants` with reserved `__STATE_BUILD_*__` identifiers and boolean/string literal values, plus an optional `browserRoot` inside the declared source root. These are explicit project facts, not inferred execution-time performance guesses. Their values participate in the source/profile identity. A fixed application may remove its dormant backend and URL-based backend choice; the uncompiled application retains its previous dynamic contract.

Constants are lowered before linking dynamic-import modules. Package exports and authored side-effect metadata must survive browser-root resolution; an unreferenced runtime class must not be retained merely because it was moved into a module-initializer closure. Real side effects remain. Both ordinary extension resolution and containment of authored local imports are checked, including root-relative and parent-relative imports. An invalid build must not replace accepted output. The lowering is one batched neutral build; final identifier minification and production environment selection remain in the browser linker.

The manifest reports each source module's contribution to the complete emitted JavaScript entry. Raw, gzip and Brotli limits still apply to the full graph and reference fallback. A `buildConstants` choice is distinct from optional measured algorithm admission: the latter's existing qualification rules are unchanged. The same application behavior suite must pass for every supported fixed configuration. Compiler and source-map assets are counted separately from runtime transfer.

The Boards integration provides an ordinary bundle-only control and applies the same compiler/bundler to baseline and state-lib. This prevents attributing ordinary minification or fewer HTTP module requests entirely to a new state algorithm. The [work-elimination ledger](../plans/2026-10-16-app-work-elimination.md) records the additional ownership-retention and keyed-view experiments; their gains must be reported separately from static linking.

#### Ownership-preserving asynchronous capture and keyed views

A capture boundary may retain a snapshot by reference only when the library's ownership registry certifies the complete immutable value. A shallow freeze or caller assertion is insufficient. Unowned inputs keep ordinary structured-clone capture. The outgoing asynchronous consumer may still require a private mutable payload; retaining a queued snapshot does not remove that public contract or the later serialization cost.

The optional `immutableRowDelta` adapter plans changed rows between immutable keyed arrays before a view is modified. Identical arrays require no work. Changed ordering, length, identity or rejected projection fields require reset. It retains no application data between calls. For each array whose identity changed, its traversal and temporary key Set are linear in the entire array length, including unchanged rows; only the subsequent view writes are proportional to changed rows. It does not claim the full incremental query/index engine described in §4.5.

The optional `patchKeyedRows` adapter is the checked view boundary for such a plan. The application supplies `locate` and `apply`; every change is located before the first write, and a missing target returns false before `beforeApply` or any `apply` runs, so the caller renders in full. An accepted empty plan still runs the optional `beforeApply` once, so a caller keeps its cleanup-before-write ordering. `beforeApply` must not replace or detach a located target, and `apply` must not do so to another change's target. Nothing is rolled back: an exception from `beforeApply` leaves the rows unwritten and one from `apply` may leave earlier rows written; either way the caller must render in full. It holds no state, assumes no DOM and adds no runtime.

The Boards application (a separate repository that vendors both adapters byte-for-byte with pinned provenance) uses this plan for completion and plain text commits, including Undo/Redo of them, to retain existing task nodes. The plan is taken against the root and board the view last showed (set by the full renderer and by each successful patch). The application clears that witness when an inline editor closes outside its settle path and when a row write throws, so a view containing editor residue or a partial write always renders in full; structural and unsupported commands, and a board that is no longer the one displayed, keep the existing renderer. The baseline entry links neither adapter. Node existence and column identity are verified before any row write. Snapshot capture and DOM reuse do not change transactions, history, persistence conflicts or input scheduling. Both features are independently omittable and are verified on actual application commands, not only a detached algorithm kernel.

Batched lowering uses the same per-file esbuild configuration discovery as the final link, rather than a configuration-free transform. Inherited TypeScript class-field semantics and local JSX factories must remain equivalent. Neutral pre-linking does not select NODE_ENV or rename late-bound identifiers: these choices belong to the final production linker. Actual emitted-program regression tests cover all three cases, alongside profile identity for transitive compiler options.

#### Audited configuration and complete output generations

The pre-link pass is one batched, unbundled compilation of authored inputs, not one compiler start per module. It preserves per-file TypeScript configuration and leaves identifiers and environment selection for the final browser linker. This also keeps local JSX factories and fragments bound correctly. Manifests record pre-link build count, file count and elapsed time.

A build-only TypeScript configuration reader inventories JSONC, multiple `extends`, package configuration and symlink targets. Resolved dependencies must remain inside the declared project, participate in the source/profile fingerprint and appear in `compilerInputs`; external inheritance is rejected explicitly. Authored entry/strategies and loaded files (including path aliases, `baseUrl` imports and JSON) must satisfy `browserRoot`. A `node_modules` path segment is not itself an exemption: inside the project root only files directly under `<root>/node_modules` count as dependencies, and outside it only files whose first `node_modules` directory belongs to an ancestor of the root (workspace-hoisted installs), so an authored `src/node_modules/...` tree is checked like any other source. Limit: a config alias that points into the project's installed `node_modules` is indistinguishable from a bare package import and is accepted; installed packages are governed by the lockfile and toolchain identity, not by `browserRoot`. Toolchain lockfiles and installed parser/bundler identities are included. Source and configuration identity are checked again before publishing output.

All generated files are prepared in a private sibling directory before publication. A short exclusive publication lock prevents concurrent directory swaps. On ordinary staging/publication errors, the prior complete generation is retained or restored; if restoration itself fails, its recovery path is preserved and reported. Cleanup after the commit point is reported separately. Unowned files are never silently deleted. This is failure-atomic generation publication, not a promise of a crash-proof filesystem or uninterrupted reads across the brief directory swap.

The baseline/candidate comparison shares the same pre-linked source cache in one bundler process: its manifest distinguishes the one pre-link pass from the two final links needed to compare full output sizes. Source-directory traversal is shared with fingerprinting, and configuration discovery probes each distinct directory once per identity check. The final source-identity recheck remains independent by design. The actual platform esbuild executable is hashed as well as its JS wrapper; ambient `ESBUILD_BINARY_PATH` overrides are rejected before execution rather than silently omitted from provenance.
