# State Management Research Brief

**Scope:** a state layer for Hyper (VS Code extension + SaaS sharing one React codebase) and for the apps users build inside Hyper (Next.js / Remix / Vite / Bun templates).
**Status:** research phase complete → this brief → briefing session → master spec + full competitor matrix + build-setup fit check.
**Date:** 2026-09-01. All versions, sizes and dates below were verified against npm / project docs on this date. Sizes are min+gzip of the whole package unless noted.

---

## 0. TL;DR

1. **The reactivity algorithm is solved; don't reinvent it.** alien-signals, Preact Signals, Svelte 5, Solid 2, Vue 3.6, Angular and the TC39 proposal all converge on the same push-pull, three-state (clean/check/dirty), lazy-computed, auto-tracking design. alien-signals is 1.9 kB / 0 deps and exposes `createReactiveSystem()` for custom node types. Wrap it behind a 5-function internal interface so it can be swapped for native `Signal` later. Do **not** build on `signal-polyfill` (Stage 1 since 2024, "not for production", no batch/effect).
2. **"No selectors, no memoization" vs the React Compiler — updated 09-03, decision #12.** Every library that gives hooks-like ergonomics without selectors tracks reads during render (Valtio `useSnapshot`, MobX `observer`, Legend, Preact `useSignals`); React Compiler v1 memoizes on reference identity and its lint flags this as "interior mutability". Our stance is not to defer to RC: memoization-as-strategy is what we set out to beat — constant busywork, and usually worse on both memory (caches) and CPU (comparisons) than precise invalidation via fine-grained subscriptions. **To-go approach: tracked mode (render tracking over per-property signals) is the default and the recommended replacement for React Compiler; snapshot mode (stable uSES references) is what the compiler auto-selects where RC is detected and active, so mixed codebases stay correct; signals-in-JSX is the experimental third mode.** Spec §5.3.
3. **"Every change is an event" and "mutable proxy ergonomics" are compatible** if the store treats a mutation as a transaction that emits **patches** (Immer/Mutative-style JSON patches + inverse patches). Commands (intent, named + args) go in one log, patches (effect) in another. That single decision gives undo/redo, devtools time-travel, cross-webview replication, persistence deltas and sync outbox for free.
4. **The data layer already exists: TanStack DB (0.8.7, MIT, still beta).** Its collection-options contract (`sync(begin/write/commit/markReady)` + `onInsert/onUpdate/onDelete` + `utils`), two-store model (synced truth + optimistic overlay, rebased on confirmation), differential-dataflow live queries, and `@tanstack/offline-transactions` outbox are exactly the middleware design described in the request notes (now REQUIREMENTS.md R-ids). Either adopt it or copy its contract; don't design a third one.
5. **Multi-context apps already converge on leader/replica stores** (a host process as the source of truth broadcasting state to embedded views — VS Code extensions, browser extensions, multi-tab apps all reinvent it, usually with hand-written race fixes). The core formalises that: patch-based replication with sequence numbers and transport drivers for `postMessage` / `BroadcastChannel` / `MessagePort` / `chrome.runtime`. (The first-customer audit that motivated this lives in the adopter-side doc, see §1.)
6. **Things in the request notes (now REQUIREMENTS.md R-ids) that reality pushes back on:** "faster than vanilla JS" (only Legend-State claims it, on krausest swap/replace rows, in beta); wasm for *object-graph* structural sharing (every JS read of a wasm-held object crosses the boundary; but shared-memory/zero-copy wasm for columnar data and query engines is a real avenue — moved to its own research track, R43/R62); Proxy `get` is ~13× slower than plain property access on current V8, so proxies stay off hot loops and need `snapshot()/toRaw()` escapes; per-item list updates in React bottom out at component granularity (no `mapArray` equivalent); uSES-driven updates are always synchronous (never time-sliced).
7. **Preliminary recommendation:** build a small own core (~4–6 kB) = alien-signals-class algorithm + lazy per-property proxy store + patch-emitting transactions + keyed collections, with a first-class adapter contract copied from TanStack DB; ship React/Vue/Solid/Svelte bindings as ~10-line uSES / `from()` / `createSubscriber` / `shallowRef` bridges; reuse existing libraries for the periphery (TanStack DB or its contract for server collections, nuqs/TanStack Router for URL, Dexie/IndexedDB persister, birpc/vscode-messenger transport, TanStack Devtools shell + Redux DevTools bridge). Details in §6; open questions in §7.

## 2. Requirements (canonical list: `packages/state-lib/REQUIREMENTS.md`)

Numbered so the master spec can reference them.

**Ergonomics**
- R1. Global store as convenient as local React hooks; no selectors or manual memoization in the common case.
- R2. Mutable-looking writes (`store.user.name = 'x'`, `items.push(...)`) with immutable, structurally shared snapshots underneath.
- R3. Colocation: state + logic + UI decomposable per page / per reusable "HOX" (reducers + selectors + actions + adapters + widgets), reusable and sliceable into hooks; no `_.get(state, 'a.b.c')`.
- R4. Per-item updates in `items.map(<Card/>)` / `<For>` without re-running the loop.
- R5. Familiar, invisible, universal — no Solid-style prop-splitting utilities required.

**Model**
- R6. All state global — including pure UI state and per-keystroke form state (while acknowledging redux-form was a mistake: the *mechanism* must be cheap enough that this is not a regression).
- R7. Every change is an event (Danny). Event sourcing + FSM concepts retained from Redux.
- R8. Signals as the reactivity primitive.
- R9. Structural sharing; memory-conscious.
- R10. Undo/redo and optimistic updates as toolkit features, not app code.

**Data / middleware toolkit (all optional, all interoperable, all replaceable)**
- R11. Auto-sync with backends via pluggable data-source middlewares: REST, GraphQL, RPC (incl. VS Code postMessage), WebSockets/SSE, RxJS, CRDT, TanStack.
- R12. Local persistence with filtering of what persists (IndexedDB etc.).
- R13. Browser history / routing / URL query as store-backed state.
- R14. Middlewares may use Web Workers, Service Workers, wasm where it pays.

**Engineering qualities**
- R15. Easy unit tests for dumb components; per-test store instances.
- R16. Easy debugging of user problems (reproducible event logs).
- R17. Easy Storybook stories.
- R18. Clean separation UI / UI logic / business logic.
- R19. Framework-agnostic core; adapters for React, Vue, Solid, Svelte, web components; works with SSR, RSC, meta-frameworks.
- R20. Zero dependencies, tiny ESM, tree-shakable, subpath exports; "faster than vanilla" as an aspiration, "never slower than Zustand/Valtio" as the bar.
- R21. Devtools that do not freeze and are not "the Redux DevTools UI".
- R22. Old browsers not supported (Proxy, ES2022+, OPFS/Web Locks may be assumed where present).

**Two audiences**: Hyper itself (webviews + SaaS, React 18 today) and user apps generated by Hyper (Next.js/Remix/Vite/Bun templates with shadcn/tamagui → SSR/RSC are concrete, not theoretical).

## 5. Tensions the spec must resolve (request notes vs reality)

1. **"No selectors" vs React Compiler.** Decide: snapshot-returning hooks with fine-grained *subscriptions* (compiler-safe, default) + optional render-time proxy tracking behind an explicit flag and lint rule. This is the single most consequential design decision.
2. **"All state global, even per keystroke" vs input semantics.** Technically fine with per-property signals + component-level subscription (a keystroke updates one signal → one `<Input>` re-renders); but controlled inputs in React 18 need the write to be synchronous within the event to avoid caret jumps and IME breakage — uSES's sync semantics actually help here. Cost lives in the *event log* and *persistence* middlewares, not the store: they must debounce/coalesce (`mergeInterval`), mark keystroke transactions as `clientOnly`/non-persisted by default, and undo must group them. Redux-form failed on mechanism (top-level re-render per keystroke + serialisation), not on the principle.
3. **"Events for everything" vs "mutable writes".** Resolved by transactions emitting patches; but decide the *granularity of the command*: is `store.user.name = 'x'` outside a named action an anonymous command (allowed, logged as `set /user/name`) or an error in strict mode (MobX `enforceActions` style)?
4. **"Faster than vanilla" — where it is and isn't winnable.** For a single raw write, hand-written vanilla is the floor a store can only approach. But for *derived data and queries* — where real apps spend their time — beating typical hand-written code is achievable: incrementally-maintained views do O(change) work where selector chains recompute; a wasm columnar query engine with shared memory (Danny-DB, R32/R62) plans and executes what reselect pyramids approximate by hand (R66 measures this). So: measurable floors for writes (≤ Zustand/Valtio on the microbench, krausest swap/replace parity, zero allocations on untouched subtrees), and an offensive goal for queries.
5. **Framework-agnostic vs "familiar and invisible".** The core can be agnostic; the *ergonomic* layer is per framework (React hook that returns snapshots; Solid that returns store proxies; Svelte via `createSubscriber`). Accept that the API surface will differ slightly per framework rather than force Solid-style utilities on React devs (R5).
6. **wasm / workers.** Core stays pure JS single-thread; a `worker` host is an optional middleware; wasm only via CRDT/SQLite plugins. Anything else is scope creep.
7. **Adopt vs build for the data layer.** TanStack DB is beta, large, and React-Query-shaped; but its contract is the right one and it ships 5 framework bindings + SSR. Options: (a) depend on it, (b) implement its collection contract natively in our core so its adapters (Electric, PowerSync, RxDB, Query) plug in, (c) ignore. (b) preserves R20 and interoperability.
8. **Backwards path for 145 hooks.** The migration story must let a hook like `useGitHubRepositories` become a collection + live query in one step, with the rest of the app untouched — otherwise adoption stalls inside Hyper itself.

## 6. Candidate architectures

### Option A — Assemble from existing libraries
alien-signals or `@preact/signals-core` (reactivity) + Mutative (patches) + `@xstate/store` or Valtio (store) + TanStack DB (server collections, outbox) + zundo-style history + nuqs (URL) + Dexie (persist) + birpc/vscode-messenger (transport) + Redux DevTools bridge.
*Pros:* fastest to prototype; each piece maintained. *Cons:* three reactivity models (signals vs xstate-store vs TanStack DB's own store) that do not share a dependency graph → glue code, double subscriptions, no unified event stream; R20 lost (dozens of kB); R1 still needs selectors at the seams.
*Depth note:* option A can only be judged at source level — the deep dives (site: Deep dives — data & reactivity; stores) study TanStack DB, signia/@tldraw/state, alien-signals, Zustand, Valtio, Jotai and Legend-State from their actual sources: module maps, code paths, gotchas, and per-library codemod feasibility.

### Option B — Own small core + adapters, borrow contracts (preliminary recommendation)
- **Core (~4–6 kB, 0 deps):** push-pull signal graph (alien-signals-class; possibly vendored `createReactiveSystem`), lazy per-property proxy store (`store.a.b.c` reads track; writes only inside `tx()`/actions), transactions emit `{txId, cause, command?, patches, inversePatches}`; keyed collections (`ids` + `byId`) as a primitive; diff-aware derived collections (signia epochs or IVM-lite); `snapshot()`/`toRaw()`; factories only, no singletons.
- **Adapters (~10–40 lines each):** React (uSES snapshot hook + optional tracked mode), Vue (`shallowRef`), Solid (`from` + `reconcile`), Svelte (`createSubscriber`), Angular (`toSignal`), Lit (Context Protocol + signals), SSR (`dehydrate/hydrate`, per-request scope via AsyncLocalStorage).
- **Toolkit middlewares (each a subpath export):** `history` (patch-based, origin-scoped, `mergeInterval`), `optimistic` (overlay + rebase, handlers await sync-back), `collections/*` implementing the TanStack DB collection contract (REST/Query, GraphQL, RPC, WebSocket, RxJS, Electric, PowerSync, CRDT), `outbox` (IndexedDB, Web Locks leader), `persist` (per-collection policy; localStorage / IndexedDB / OPFS-SQLite / VS Code `setState`), `url` (nuqs-style parsers, router-aware), `remote` (patch replication over `{post,onMessage}`; drivers: VS Code, BroadcastChannel, MessagePort, chrome.runtime), `worker` host, `devtools` (event stream → TanStack Devtools panel + Redux bridge + `devtoolsFormatters`), `fsm` (xstate-store-like typed transitions on a slice).
- **Ergonomic layer per audience:** Hyper: `defineComplex()` (HOX) = slice + actions + collections + adapters + widgets, mounted per page; user apps: same API, template presets for Next/Remix/Vite.
- **Compiler (`state build`) is part of B, not an add-on:** per-project specialisation (unused modules stripped, proxy reads rewritten to signal reads on hot paths, derive chains fused, typia-style validators generated, React mode per component, devtools-maps emitted) — §5 of the spec; without it B is merely another library, with it B is infrastructure (F2).
- **Query layer:** complex derived data targets the Datalog-family engine (Danny's Rust→wasm database, Datomic lineage — see the Datomic query reference) mounted through the worker host, with diff-aware `derive.collection` (IVM-lite) as the pure-JS tier (R32, R66).
*Pros:* meets R1–R21 by construction; one dependency graph → one event stream → one devtools; interoperable with the TanStack ecosystem via the contract. *Cons:* we own a reactivity runtime (mitigated: the algorithm is small and settled; vendoring alien-signals is ~600 lines); adapters × frameworks maintenance; needs a benchmark suite from day one.

### Option C — Adopt TanStack DB + a signals lib, thin layer
TanStack DB for all server and most client data (local-only collections), a signals library for UI state, a thin `defineComplex` on top.
*Pros:* least code, rides TanStack's SSR/devtools/framework work. *Cons:* beta with breaking minors; bundle far above R20; UI state and DB state still two worlds; no proxy ergonomics; no patch/event stream for UI state; devtools not ours.

**Recommendation for the briefing:** pursue **B**, prototyped in two weeks as a spike: core + React adapter + `remote` driver for VS Code + one collection (GitHub repositories via the TanStack DB contract) + devtools event stream, measured on js-reactivity-benchmark and krausest, and used to replace `shared-editor-state` + `StateHub` + `useGitHubRepositories` inside Hyper as the acceptance test. Keep **A** as the fallback if the spike misses the size/perf bars.

## 7. Open questions for the briefing

1. **Compiler stance (R1):** default to compiler-safe snapshot hooks with opt-in tracked mode — agreed? Will Hyper enable React Compiler (currently off)?
2. **Command granularity (R7):** are anonymous writes outside named actions allowed (logged as `set` patches), or strict-mode errors? Does Danny's "events for all changes" mean *commands* (intent), *patches* (effect), or both logs?
3. **Keystroke policy (R6):** default `clientOnly` + non-persisted + undo-grouped with `mergeInterval` ≈ 500 ms — acceptable? Any state that must *never* be global (e.g. Monaco editor buffers, canvas drag transients at 60 fps)?
4. **Data layer (tension 7):** depend on TanStack DB, implement its contract natively, or ignore it?
5. **Leader for SaaS:** in VS Code the extension host is the leader; in SaaS is the leader the tab, a SharedWorker, or the server (Electric/Zero-style)? Does Hyper need multi-tab consistency today?
6. **Undo scope:** one global history or per-domain stacks (canvas vs inspector vs file edits)? Must undo survive reload (persisted inverse patches)?
7. **User apps:** which templates are first-class (Next.js App Router with RSC? Remix/React Router 7? Vite SPA?) — this fixes the SSR/RSC scope for v1. Are Vue/Solid/Svelte adapters v1 or v2?
8. **Framework versions:** Hyper on React 18.3 — is React 19 (use/useOptimistic/Activity) in plan? Bun/Vite-only builds or also webpack/Next's Turbopack in user apps?
9. **Devtools UX:** in-app panel (TanStack Devtools shell), VS Code panel, or browser extension? Is a Redux DevTools bridge wanted for familiarity?
10. **Size/perf bars (tension 4):** concrete numbers to sign off (core ≤ 6 kB? React adapter ≤ 1 kB? ≥ Zustand on benchmark X?).
11. **statebus:** does Danny want to evolve it into this (keep name/API ideas like `ByID`, `substateInterest`) or treat it as a reference?
12. **Licensing/positioning:** internal to Hyper, or an open-source library that user apps depend on (implies semver discipline, docs, and a name)?
13. **Migration:** big-bang or per-page HOX migration starting with `shared-editor-state` / `StateHub`?
